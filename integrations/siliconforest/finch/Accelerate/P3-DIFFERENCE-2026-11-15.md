# Display-P3 difference audit, 15 November 2026

The retained `80` versus native `82` is a real profile-selection bug, not merely
different color-matching arithmetic. The original exact same Linux-built test
has SHA-256 `8cbc88cd76169940a8e3c75fae1a9a665895614e44937109bd4288ec19847041`.
Its sole raw difference is `sRGB to Display P3 (coarse)`, in
`runs/sffinch/vimage-stage-v2/candidate.json` versus
`m5-vimage-v1-reference.json`. Those receipts and the original masks are unchanged.

## Cause and narrow correction

SiliconForest's named spaces preserve `CGColorSpaceGetName` but have no ICC data.
Finch's `vImage/utilities.c:profile_for` first tries ICC data, then maps by model.
Thus named Display-P3 falls through the RGB fallback to the sRGB profile. A
matching RGB component count cannot represent its different primaries.

The fixture's first random input uses seed 12345, LCG constants 1664525 and
1013904223, five 216-byte rows. Treating its first 13 pixels per row as RGBX,
leaving RGB unchanged and writing opaque padding gives sum 41167 and exactly
the observed coarse value `80`. This independently reproduces an identity
conversion's checksum; it is not evidence of a correct P3 conversion.
`p3-colorimetry.py` independently derives the two RGB-to-XYZ matrices from
public xy chromaticities, linearizes sRGB, changes primaries and applies the
common transfer function. Nearest U8 rounding predicts sum 42312 and coarse
`82` for proper P3, agreeing with native. It does not use ColorSync/skcms or
copied ICC data and is not a substitute for target execution.

Patch `0005-vimage-named-display-p3.patch` supplies one missing adapter: after
explicit ICC data has taken priority, a retained Display-P3 name selects our
existing real `kColorSyncDisplayP3Profile`. No matrix, white point, transfer
function or pixel output is hardcoded to match a fixture. ColorSync and
CoreGraphics sources are unchanged. Other named spaces lacking ICC profiles
are outside this small correction and remain unaudited.

Apple's [Display-P3 definition](https://developer.apple.com/documentation/coregraphics/cgcolorspace/displayp3)
specifies P3 primaries, D65 white and the sRGB transfer function. The pinned
ColorSync implementation already generates that profile with D50-adapted ICC
colorants and its chromatic adaptation tag. The [W3C colorimetry definition](https://www.w3.org/TR/css-color-4/#predefined-display-p3)
provides the same primaries, white and transfer parameters. This audit does
not establish general ICC/profile/CMM conformance.

## Independent controls

`p3-probe.c` converts black/white, RGB primaries, two neutral grays and three
mixed colors using both unsigned-byte RGBA and float RGBA. It compares identity,
named Display-P3, an explicit ColorSync P3 profile, and a profile generated by
`vImageCreateRGBColorSpaceWithPrimariesAndTransferFunction` from public
colorimetry. All use relative-colorimetric intent, no output device and no files.

The Linux-built portable program has SHA-256
`ad7d0b7dcef3d4ccb9e99d91300535832a5b29f04f59a8625bcf4b51f60b1ea7`.
The native reference completed in a fresh M5 temporary directory with SHA-256
verification, a 30-second bound, no DYLD overrides and directory removal.
Only the program's stdout/stderr returned. On native, all three P3 forms agree
exactly for these inputs in both formats. Pure red becomes U8 `(234,51,35)` or
float approximately `(0.917470,0.200369,0.138521)`; it remains `(255,0,0)` under
identity. Grays stay neutral, as required by their common white/transfer encoding.

M1 baseline and fixed-prefix checks completed at 19:39:19–21Z, after the actual
kernel recovery/UART release and DESK test release, under gui.lock and bench.
Stages are `vimage-p3-baseline-v1` and `vimage-p3-fixed-v1`. The baseline reports
named P3 `icc=0 name=1`; pure red remains `(255,0,0)` while its explicit ICC
control converts correctly. Its named U8 pixels equal identity exactly; the
F32 logical identity round trip adds only the CMM's small numerical error.
The private correction makes all three P3 representations agree exactly with
each other in U8 and F32. Pure red becomes `(234,51,35)`.

The unchanged original full vImage comparison now reports **MATCH**, including
`sRGB to Display P3 (coarse): 0 82` against native `82`. The new focused probe's
raw verdict remains **DIFF**, with its complete component data retained:

| Focused comparison against native | U8 | F32 |
|---|---|---|
| Identity | Exact | Exact |
| Named P3 | One component differs by 1 LSB | Maximum error 0.000045597, RMS 0.0000194353 |
| Explicit P3 ICC | Same residual | Same residual |
| P3 generated from public parameters | Same residual | Same residual |

These small residuals are CMM/conversion arithmetic differences shared by the
explicit-profile controls, rather than the missing P3 mapping. They are bounded
observations, not an invented success tolerance or a claim of formal CMM
conformance. The U8 mismatch is mixed-color green: native 127, ours 126; native's
own F32 result multiplied by 255 is about 126.488, illustrating that its U8 and
F32 pipelines need not be identical nearest-rounding calculations. The new
probe also deliberately retains native `icc=1` versus retained CG's `icc=0`.
No raw output, masks or existing coarse checksum policy was changed to hide this.

The corrected private vImage cold SHA-256 is
`6af99199a1ab1c6f7fe47acc13993bb10e7b281f61328ffbd6f460b40a970b71`,
verified on the M1 before execution. The canonical provider is unchanged.
`compare-p3.py` records complete component errors and named-versus-ICC/identity
comparisons without replacing the raw harness result or adding a tolerance.
Native receipts are `m5-vimage-p3-v1-reference.json`; fixed-stage `comparison.json`
and `measurements.json` record the distinct raw grades and numerical evidence.
