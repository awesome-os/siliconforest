## Goal
The Claude Code CLI (Anthropic's vendor binary for macOS arm64, a Bun program) runs on SiliconForest on the M1: interactively in a terminal and with `-p`. GitHub issue 51.

## Status (13 November 2026)
**The unmodified vendor binary runs on the M1 from the installed disk** (boots dr46, dr47): `claude doctor` runs to its end, `claude -p hello` answers "Not logged in · Please run /login" (nobody is signed in), `claude` on a terminal shows its first screen and, after one Enter, the login-method screen. Nothing was signed in; what comes after a sign-in is untested.

It was never the kernel, the hardened runtime, code signing or the JIT. **The process was ended by our own libxpc**, in userland, and the fix is one patch to libSystem. The kernel on SFBOOT is unchanged (`sf/kernel.bin` `093b61f1…`).

The binary on the disk root: `/usr/local/lib/claude-code/2.1.322/claude` (323,702,464 bytes, sha256 `a9d23794…`, the vendor's manifest checksum, read again on the M1 in dr46), `/usr/local/bin/claude` -> `../lib/claude-code/2.1.322/claude`. The copy `claude.sf` of boot dr45 is removed (dr46).

## The kill site and the cause
Console of every killed start (dr42, dr44, dr45; `runs/m1-desktop-010/pcie-enum-attempt-dr44/guest/console.bin`, lines 658 to 660):
```
CODE SIGNING: cs_invalid_page(0x117bb8000): p=349[claude] final status 0x20010000, allowing (remove VALID) page
PureDarwin libxpc misuse: Unknown XPC type
Failed to send exception EXC_CORPSE_NOTIFY. error code: 5 for pid 349 proc=? etype=10 subcode=0x700000002
```
- The middle line is the reason; it was in all three consoles and was overlooked. It is printed by `src/Libraries/XPC/libxpc/xpc_debug.c:13` (`xpc_api_misuse`), which then calls `abort_with_reason(OS_REASON_LIBXPC, 2, …)` (line 30).
- `subcode=0x700000002` is that exit reason: `osfmk/kern/thread.c:572` hands `proc_encode_exit_exception_code()` (`bsd/kern/kern_exit.c:472`: namespace << 32 | code) to `task_deliver_crash_notification` (`osfmk/kern/task.c:2425`). Namespace 7 is `OS_REASON_LIBXPC`, code 2 is the one `xpc_api_misuse` uses. (The `sftp-server` line `0x20000000a` is namespace 2, `OS_REASON_SIGNAL`, signal 10.) The shell sees 137 for claude because Bun handles SIGABRT and the abort's fallback is a kill; a plain C program dies with 134 (the probe below).
- The caller of `xpc_api_misuse("Unknown XPC type")` is `xpc_copy_description()` (`libxpc/xpc_misc.c:198`): it had text for dictionaries, arrays, strings, numbers, dates, UUIDs, endpoints and null, and ended the process for anything else, among them a **connection**.
- Who asks for the description of a connection: Security.framework. Bun `dlopen`s `/System/Library/Frameworks/Security.framework/Security` and calls `SecItemCopyMatching` (the strings sit together in the binary; Claude Code reads its credentials from the keychain at start). There is no securityd here, the request fails, and Security's client builds its error text with `xpc_copy_description(connection)` (`src/Libraries/Security/apple/OSX/sec/ipc/client.c:407`). That chain is read from the sources and the binary's strings, not from a backtrace; the two experiments below are what establish it.
- Why `--version` and `--help` ran: they do not touch the keychain. Why `BUN_JSC_useJIT=0` "was not killed": Bun without its JIT has no `SharedArrayBuffer` and the program stops with that error before it reaches the keychain. The JIT was a coincidence.
- Why the Homebrew stream's QEMU runs (c2 to c5) reached the login screen: that image had no Security.framework (the log said "[keychain] readAsync failed"), so the `dlopen` failed and the program fell back. The M1's root got Security.framework with the `sys` part (for curl and ssh). It was the root's content, not the machine: **QEMU kills it exactly like the M1** on the M1's root image.
- The line `cs_invalid_page … allowing (remove VALID) page` is harmless and appears for every program.

## The fix
`integrations/puredarwin/libsystem-default/patches/xpc-copy-description-never-aborts.patch`, in the patch list of `libsystem-default/build-libsystem.nix` (the lab's default libSystem; libxpc is linked into `libSystem.B.dylib`): `xpc_copy_description()` describes a connection (`<name = …, remote port = …>`), data (`<N bytes>`) and a double, and prints the object's address for any type it has no text for, instead of ending the process. The UUID branch called `free()` on a stack buffer; that line is gone. Nothing is granted to anybody: a description is a string for a log line. No kernel change, no change to the AMFI stand-in.
- Build: `/nix/store/6afqk3511r43cyfm0a9kcfz4001xbfm1-puredarwin-libsystem-default-0.1`, `usr/lib/libSystem.B.dylib` 4,338,894 bytes, sha256 `bebd667b…` (before: `rdi193a9…`, 4,338,830 bytes, `09b83541…`, which is byte for byte the file of the root image). The recipe's `dyld`, `libdyld.dylib` and `notifyd` also differ from the build before (not looked into; the root keeps its own, only the one file was replaced and both QEMU and the M1 run that mix).
- The root build: `artifacts/m1-desktop-010/apcie-port-candidate-003/mapping.json` (not in git) names the new store path for `/usr/lib/libSystem.B.dylib` since 13 November (copy of before: `mapping.json.before-xpc-fix-20261113`); `libsystem-default/DEFAULT.txt`. A root image built from now on has the fix; the image `pcie-enum-candidate-sw01/ramdisk.img` the disk root was copied from does not.
- On the M1's disk: `/usr/lib/libSystem.B.dylib` is the new file since boot dr46, the file of before is `/usr/lib/libSystem.B.dylib.old` (a second name of the same inode, bit for bit). Way back: `ln /usr/lib/libSystem.B.dylib.old /usr/lib/libSystem.B.dylib.back && mv -f /usr/lib/libSystem.B.dylib.back /usr/lib/libSystem.B.dylib` (and claude is killed again).
- Not fixed, same class: `xpc_connection.c:662` ("Function unimplemented"), `xpc_type.c:586` (`xpc_equal` of some types), `liblaunch.c`, `xpc_dictionary.c` (serialising shared memory or an error) still end the process through `xpc_api_misuse`. None was reached by Claude Code. Any program that ends with `PureDarwin libxpc misuse: …` on the console and `subcode=0x7000000NN` is one of these; the text names which.
- Still true: there is no securityd and no keychain. `SecItemCopyMatching` fails (now with an error instead of a kill) and Claude Code uses its file fallback; whether a sign-in then stores its credentials in `~/.claude/.credentials.json` is untested.

### Replacing libSystem on a running system (`tools/sf_userland_push.sh libsystem <new libSystem.B.dylib> <sf-xpc-probe>`)
A libSystem that does not load leaves a root on which nothing starts, and repairing that from Linux would be a write to the partition. So `userland/sf-libsystem-install.sh`, on the target: (1) the new file, written beside the old one as `libSystem.B.dylib.sf-new`, has the SHA-256 of the host's build; (2) it loads there: `userland/jit/sf-xpc-probe.c` (the very call that ended claude) is ended with the library in use and says `SFXPC ok` with `DYLD_LIBRARY_PATH` pointing at a hard link of the new file, which only the fixed library can do; then `ls`, `sh`, `sha256sum`, `node`, `claude --version` run with it; (3) only then the file in use gets the second name `.old`, the new one is renamed over it, and new processes are started without any DYLD variable. A failure before (3) changes nothing (rehearsed: run cj5 stopped at a wrong path in my own check and left the system as it was). Rehearsed in QEMU (cj6: on the disk afterwards `libSystem.B.dylib` = `bebd667b…`, `.old` = `09b83541…`, `e2fsck -fn` clean), then run on the M1 in dr46 with the same lines.

**A finding on the way: the SHA-256 of a library in use is not the file's.** The guest's `sha256sum /usr/lib/libSystem.B.dylib` gave `83e40e0b…` where the disk has `09b83541…` (and `590baea6…` for `bebd667b…`). The tool is right about what `read(2)` returns: upstream's kernel rewrites pointer-authentication instructions in the page cache when a page of a signed file is first mapped executable (`osfmk/vm/vm_fault.c:8964` to `9050`, `pd_pac_lower_page`, called from `vm_page_validate_cs_mapped_slow_internal`), and `read` of the same file then returns the rewritten page. In libSystem the difference is four words in one page, `d50320ff` (`xpaclri`) read as `d503201f` (`nop`); the disk keeps the original (compared from the host on the image after cj4 and cj6). Consequences: hash a pushed file before anything runs it (the push tool does; its earlier verifications were of files not yet executed); a `cp` of a program or library in use writes the rewritten bytes into the copy (the reason `.old` is a hard link); such a hash depends on which pages have been executed.

## The sibling entitlements (what a vendor's JIT program carries)
Measured with `userland/jit/sf-jit-test.c`, signed three ways by `userland/jit/sf_cs_sign.py` (`build-jit-test.nix`): the linker's ad-hoc signature (as node); hardened runtime with `allow-jit`, `allow-unsigned-executable-memory`, `disable-library-validation`, `disable-executable-page-protection`; hardened runtime with no entitlement. **All three get the same answers, in QEMU (cj6, `DEBUG_ARM64_VIRT`) and on the M1 (dr46, dr47, `DEVELOPMENT_ARM64_T8103`)**: this kernel does not look at the hardened-runtime flag or at these entitlements at all. The process status shows the flag (`0x20010001` against `0x20020001`), nothing acts on it (`CS_RUNTIME` is read in one accessor, `bsd/kern/kern_cs.c:1747`; the policy that turns it into restrictions is Apple's AMFI, which this system does not have).

| Entitlement | What it is for | Here | Would our kernel trip a program that has it? |
|---|---|---|---|
| `com.apple.security.cs.allow-jit` | `mmap(MAP_JIT)`, RWX | **given to every process** (case `map-jit` ok, all three). `kern_mman.c:586` asks the code-signing monitor (none: allowed), `:597` asks the MAC policies, and the AMFI stand-in has no `proc_check_map_anon` hook. `pthread_jit_write_protect_np()` is a no-op in this libpthread (`pthread/compat-include/os/thread_self_restrict.h` says "not supported"), so a MAP_JIT region is simply RWX for all threads | No |
| `com.apple.security.cs.allow-unsigned-executable-memory` | executable memory that is not MAP_JIT | write, then `mprotect(RX)`, then run: **works for every process** (`rw-then-rx` ok). `mmap`/`mprotect` to **RWX without MAP_JIT is refused for every process**, entitled or not (`rwx-anon`: EACCES; console `vm_map_enter: curprot cannot be write+execute. failing`, `osfmk/vm/vm_map.c:3180` to `3215`: on arm64 the check does not depend on the process's enforcement flag) | Only a program that maps RWX without MAP_JIT. As I read the same code, that is also what Apple-silicon macOS does (not verified on a Mac); JavaScriptCore and V8 use MAP_JIT |
| `com.apple.security.cs.disable-library-validation` | load libraries signed by somebody else | **nothing validates** (`dlopen` of Security.framework ok in all three; `kern_descrip.c:4430` and `ubc_subr.c:5709` go to MAC hooks the stand-in does not implement or answers with success) | No |
| `com.apple.security.cs.disable-executable-page-protection` | modify the program's own code pages | **works for every process** (`text-write` ok: `vm_protect(VM_PROT_COPY)` on a page of `__TEXT`, change it, run it). No process has `CS_ENFORCEMENT`, `CS_HARD` or `CS_KILL`; modified pages are "allowed" (the `cs_invalid_page … allowing` line) | No |
| `com.apple.security.device.audio-input`, `com.apple.security.automation.apple-events` (Claude Code has them) | TCC | no TCC here; not looked at | not measured |

So none of them trips, and the reverse is the weak point: **these behaviours are not entitlement-gated here; everybody has them.** The system validates no signature chain: the entitlements the AMFI stand-in does read (`amfi_entitlements.cpp`, for the few privileges it grants) are whatever XML the binary's own signature carries, and `sf_cs_sign.py` shows that anybody can write that. Making MAP_JIT depend on `allow-jit` for hardened-runtime programs (a `proc_check_map_anon` hook, about twenty lines) would match macOS and protect nothing; not done, and I do not propose it.

One more thing the test found, unrelated to signing: **`dlopen()` in a child of `fork()` fails** ("image not loaded", any library, all three programs, run cj6); in the parent it works. Not investigated.
