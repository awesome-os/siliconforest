## Goal
Hardware video decode on the M1 (J293, T8103) through the SoC's Apple Video Decoder (AVD): a kernel driver ported from the Omacom Linux tree, a userland decode interface, a video player that uses it, and the decode side of VideoToolbox so that applications written for macOS (Firefox) get hardware decode.

Owner's words: "we want avd support, port that from linux and make sure we have hardware decoded video support properly, like for playing videos etc, in firefox, and lets get a video player working that uses avd".

## For the owner, the morning of 2026-11-12
- **What works on the M1 now**: the video decoder block decodes H.264, HEVC (8 and 10 bit) and VP9 under our kernel, bit-identical to software decode (12,146 frames checked, including all 63 progressive H.264 conformance streams of the JVT suite). A player, `pdvideo`, plays a 1080p H.264 film clip with sound on the desktop through it: a full minute, every frame shown, none dropped, at 16 % CPU instead of 31-37 % for software decode. VideoToolbox, the interface Firefox uses for video on macOS, decodes through the hardware from a test program.
- **To see it yourself** (about 50 s to the desktop; ends by itself after the minutes given, default 30):
  `AVD_INTERACTIVE=1 integrations/puredarwin/m1-avd/tools/avd_desktop_boot.sh av30 30`
  then in a terminal on the desktop: `/usr/local/bin/pdvideo /private/var/avd/bbb-1080p-h264-60s.mp4` (q or Esc ends it; `--hwdec=none` for software, `--volume=0..100`). End the session early from the workstation with `tools/gpu_desktop_stop.sh`. This interactive mode stages exactly what boot `av19` staged, but the mode itself (no play list, speakers not held down, your shell starting the player) has not been booted: if the player does not find the display from your terminal, set `XDG_RUNTIME_DIR=/private/var/run/gpu-desktop WAYLAND_DISPLAY=wayland-0` in front of the command.
- **What to look at**: whether the picture is right and smooth and the sound in sync. Nobody has seen it: every result here is from logs and frame hashes, and the unattended runs kept the speakers 20 dB down.
- **Not done**: Firefox itself (it does not run on the system yet; its decode layer is ready for the Cocoa stream to pick up); zero-copy to the compositor (frames are copied; needs dma-buf export and NV12 import in Chonkstep); mpv (a small player was written instead); pause/seek/subtitles in the player; the device is root-only; AV1 is not in this SoC's decoder.
- **Decisions for you**: put `PDAppleAVD` into the default collection (it is inert without `pdavd=1`)? Build the decoder's firmware from its MIT source and ship it, instead of taking the file from the M1's Linux per boot?

## Facts
- **Hardware** (Apple device tree `/arm-io/avd`, Linux `avd@269080000`): one `reg` 0x268000000 + 0x1404000; the driver uses `code` +0x1080000 (0xc000: program memory of the block's Cortex-M3), `mbox` +0x1098000, `ctrl` +0x1100000 (decode control and the instruction FIFOs). Power: `clock-gates` 0x12b 0x12c 0x12d. Interrupts AIC 540, 541 (541 is mailbox 1, the one used). Own DART `/arm-io/dart-avd` at 0x269010000 (T8020 type, 16 KiB pages, `clock-gates` 0x145, AIC 547), stream 0.
- **Firmware: yes, and it is open.** The Cortex-M3 runs the MIT-licensed firmware of github.com/aurora-silicon/avd-fw (Arch package `avd-fw 0.1-1` on the M1's Linux). T8103 image: `apple/avd-fw-v2-t0.bin`, 49,152 bytes, sha256 `0c80d2a0…5346ad`. The driver copies it into the `code` region at every start, as Linux does. It is **not in the repository**: copied read-only from the M1's Linux into `private/firmware/apple/` and staged per boot as `/Library/Firmware/apple/avd-fw-v2-t0.bin`, like the Wi-Fi and Touch Bar firmware. Because it is MIT source, it could instead be built and shipped from source (clang + lld, `make AVD_VER=2 AVD_TIER=0`); that build was not done here (the clone is in `runs/avd/fw-src`): the owner's decision.
- **Kind of decoder**: stateless. Linux exposes it as a V4L2 stateless ("request API") decoder: userspace parses the bitstream and passes parameter structures per picture; the driver turns them into an instruction stream for the block. On the Omacom system the userland is `libva-v4l2_request-avd` under FFmpeg's VA-API hwaccel (also used by mpv and Chromium there).
- **Codecs in the Linux driver for T8103**: H.264 (also 4:2:2 and 10 bit, no interlace, no slice groups), HEVC (Main, Main 10), VP9 (profiles 0–3 by the tables). **No AV1 on this SoC** (the block of T8122 and later has it). Maximum 4096x4096 for H.264 and VP9. Proven here: 8-bit 4:2:0 only, up to 1920x1080.
- **Hypervisor**: nothing special. Our boots run as a guest of the m1n1 hypervisor, which passes the block's registers, its DART, its power domains and AIC interrupt 541 through; no launcher change was needed.
- **Patents**: H.264/AVC, H.265/HEVC and VP9 are involved. Nothing was held back for that reason.

## Layer 2: `PDAppleAVD.kext` (`integrations/puredarwin/m1-avd/`)
- **A port, not a rewrite**: the Linux codec files (`avd-h264.c`, `avd-hevc.c`, `avd-vp9.c`), the hardware file (`avd-hw.c`), the instruction definitions and the V4L2 helper libraries they use (`v4l2-h264.c`, `v4l2-vp9.c`) are in `kernel/linux/` **byte-identical** to the Omacom tree at `6a08a08e` (the host test checks this against the tree). They compile against a small stand-in for the Linux interfaces they use (`kernel/shim/pd_linux_shim.h`). `kernel/pd_avd_core.c` is `avd-drv.c` + `avd-v4l2.c` without V4L2: buffers, job tables, FIFO submission, the mailbox interrupt protocol, the 2 s watchdog with a reset of the block. `kernel/PDAppleAVD.cpp` is the platform side (power, mappings, firmware file, interrupt, device node); `kernel/pd_avd_dart.cpp` maps every buffer in a 2 GiB address space behind the decoder's DART.
- **Off by default**: does nothing unless `pdavd=1` is in the boot arguments (`2`: info lines, `3`: debug). Even then nothing is powered before the first open of `/dev/pdavd`. GPL-2.0; notices in `NOTICE`, `Info.plist` and every file.
- **Collection**: `build-kc.nix` = the current default collection (`m1-boot-speed/build-kc.nix`) + this kext (185 kB before stripping). Booted as `/nix/store/rzryn4avl3hcy31hjx5lakmkhdgaqfw4-puredarwin-kc-arm64-0.1`. **Proposed for the default collection** (it is inert without `pdavd=`); not put there by this stream.
- **Host tests** (`host-test/run-host-tests.sh`, no hardware): (1) the Linux files are identical to the tree's; (2) core + codec files build with `-Wall -Werror` under ASan/UBSan against a stand-in decoder; (3) every recording replays with all decodes succeeding, no sanitizer report, no device memory left, and a repeatable instruction stream. All pass for the 77 recordings of this night (14 clips of our own, 63 JVT conformance streams). What this is and is not: because the generators are the Linux files themselves, "bit-identical instruction streams" holds by construction for the generators; the test does **not** compare against streams captured from a running Linux (that would have needed playback on the M1's Linux, which was not allowed tonight). The proof that the streams are right is the hardware result below.
- **Hardware result, boot `av02`** (hypervisor boot, no desktop; `tools/avd_boot.sh`): each clip was parsed on the workstation by FFmpeg's `pdavd` hwaccel into a recording of the driver calls (`PDAVD_DEVICE=record:<file>`), the recording was replayed on the M1 into the real decoder (`pdavd-replay`), and the MD5 of every decoded picture (visible NV12 area) compared with `ffmpeg -pix_fmt nv12 -f framemd5` of a software decode on the workstation (`tools/avd_compare.py`).

## Layer 3: `/dev/pdavd`, `libpdavd`, FFmpeg hwaccel
- **`/dev/pdavd`** (`include/pdavd/pdavd_ioctl.h`, five ioctls): create a context for a codec and size with N decoded buffers; map a decoded buffer read-only into the caller; decode (parameter structures + coded data + destination buffer + a timestamp that names the picture for later references); destroy. The parameter structures are Linux's `struct v4l2_ctrl_*` (`include/pdavd/v4l2-controls.h`, the unchanged uapi header, which is dual-licensed BSD-3-Clause).
- **`libpdavd`** (`user/pdavd.c`, MIT): thin wrapper, plus the recording backend (`PDAVD_DEVICE=record:<file>`) used by the tests.
- **FFmpeg hwaccel `pdavd`** (`ffmpeg/0001-pdavd-hwaccel.patch` against FFmpeg 8.1.2, LGPL): hardware device type `pdavd`, pixel format `AV_PIX_FMT_PDAVD`, hwaccels `h264_pdavd`, `hevc_pdavd`, `vp9_pdavd`. FFmpeg does the parsing, reference lists, reordering (display order) and timestamps; the control filling is adapted from the V4L2 request API hwaccels (Jonas Karlman's FFmpeg branch), which is the code the Linux driver is used with. Any FFmpeg program gets hardware decode with `-hwaccel pdavd` / an hw device of that name; frames are downloaded with `av_hwframe_transfer_data()` (NV12). Colour metadata (matrix, range, primaries, transfer) is FFmpeg's, from the stream.
- Builds: `build-user.nix` (libpdavd, `pdavd-replay`), `build-ffmpeg-pdavd.nix` (FFmpeg for our userland with the hwaccel: `/nix/store/a2828v5xbwwyysh35mq0j2r061jzfbga-darwin-lab-ffmpeg-arm64-darwin-pdavd-8.1.2`).

## Layer 5: VideoToolbox (`integrations/puredarwin/m1-avd/videotoolbox/`)
**Firefox playback is not proven, and cannot be until Firefox runs on this system.** What exists is the layer Firefox (and every other macOS application) decodes through, working on the M1 from a test program that uses only the public API.
- `VideoToolbox.c` + `VideoToolbox.h`: a replacement for the tree's `src/Frameworks/VideoToolbox/VideoToolbox.c` (which says "the codecs this system has, which is none"). A `VTDecompressionSession` is a libavcodec decoder with the `pdavd` hwaccel when `/dev/pdavd` is there, libavcodec's software decoder otherwise (or when the caller sets `EnableHardwareAcceleratedVideoDecoder` to false; `RequireHardware…` fails without the device). Input: one sample per `CMSampleBuffer`, format description from `CMVideoFormatDescriptionCreate` with the `avcC`/`hvcC` atom in `SampleDescriptionExtensionAtoms` (what Firefox and FFmpeg build); H.264, HEVC, VP9. Output: `CVPixelBuffer` NV12 (`420v`/`420f`, or planar `y420`/`f420` on request) with the stream's colour attachments, in **decode order inside the `DecodeFrame` call**, as Apple's decoder delivers them, each with its `sourceFrameRefCon` and times. `VTIsHardwareDecodeSupported`, `VTSessionCopyProperty(UsingHardwareAcceleratedVideoDecoder)`, `CanAcceptFormatDescription`, `WaitForAsynchronousFrames`, `FinishDelayedFrames`, `Invalidate` are implemented; the session is a CF object. The compression side is unchanged (no encoder).
- For decode order the FFmpeg patch has a hook (`AVPDAVDDeviceContext.picture_decoded`): libavcodec itself only outputs in presentation order.
- `build-videotoolbox.nix` builds the framework against the arm64 CoreFoundation, CoreMedia and CoreVideo that the Cocoa stream builds from the pinned tree (its `arm64.nix` is imported, nothing of that stream is edited). FFmpeg is linked statically and hidden (only `VT*`/`kVT*` are exported).
- **Hardware result, boot `av06`** (`tools/avd_vt_boot.sh`; `vt-decode-test`: libavformat only demultiplexes, then format description from the atom → session requiring hardware → `CMSampleBuffer` per sample → `CVPixelBuffer` in the callback → MD5 of its planes, compared with the workstation's software decode):

- **What the Cocoa stream needs to pick up** (nothing of theirs was edited):

The picture is copied into the pixel buffer in either case.

## Not done / known limits
- **No dma-buf export, so no zero-copy to the compositor or Mesa.** Decoded buffers are kernel memory mapped read-only into the process; a player copies each frame (about 3 MB at 1080p) into a wl_shm buffer or a GL texture. Zero-copy needs three things, none started: the decoded buffers exported as dma-bufs that the asahi DRM driver can import (PRIME import in the LinuxKPI layer of `m1-drm72`); NV12 in Chonkstep's linux-dmabuf (today `crates/wm-darwin/src/server.rs` refuses buffers with more than one plane and `glrender.rs` accepts XR24/AR24 only; wl_shm is ARGB/XRGB only); a YCbCr sampling path in its GL renderer. No compositor change was made by this stream.
- The RAM root of the test boots has room for about 15 MB of player and clips; larger content needs another way in (the base image, or fetching over Wi-Fi).
- **The device node is root-only (0600)**: the Linux codec files trust the parameter structures to the degree V4L2's control framework validates them, and that validation is only partly ported (sizes and array bounds are checked; field ranges are not). Opening it to unprivileged users needs that validation.
- 4:2:2 output is in the driver but nothing was decoded in it. 10-bit is proven for HEVC Main 10 only; the player shows 10-bit through swscale, and VideoToolbox does not deliver 10-bit pixel buffers yet.
- One decode at a time (as Linux's mem2mem); several contexts can exist (8). No runtime power management: the block is on while a context exists.
- Interlaced H.264 is refused by the driver (as in Linux). Resolution changes inside a stream need a new context (FFmpeg does that).
- Conformance: only H.264 has been run against a conformance suite (JVT, progressive 8-bit 4:2:0). The interlaced, 4:2:2 and 10-bit JVT streams (9 of the 72 fetched) were not run: the driver refuses interlace. HEVC and VP9 were checked with encoder output only (x265, libvpx), not with the JCT-VC or Argon suites.
